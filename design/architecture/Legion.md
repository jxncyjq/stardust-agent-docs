## 一、项目概述

### 1.1 产品愿景

以企业管理的方式组织智能体团队，让 AI 像真实团队一样协作完成复杂业务。

用户不再"使用 AI 工具"，而是"管理一支智能体团队"——定义组织架构、分配角色职能、编排业务流程、设定目标预算，智能体团队自主协作执行，用户作为决策者审批关键节点。

### 1.2 产品定位

本系统是一个**多智能体团队协作的业务流创作与运行平台**，围绕三个自研核心引擎构建：

- **MaaS 模型调度层**——统一纳管多厂商、多类型大模型，为不同智能体按需分配最优推理资源
- **AI Agent 引擎**——自研智能体运行时，具备自然进化与持续学习能力，Agent 越用越强
- **LLM Wiki 知识库引擎**——人类与智能体共建共享的知识基座，让组织知识在人机之间无缝流转

产品以市场化的形式，把Skills/Agent/knowledge/mcp，以及未来智能用得到的组件，作为交易平台，可以由用户自由选择和搭配

### 1.3 目标用户

| 用户类型     | 典型场景                    | 核心诉求                 |
| -------- | ----------------------- | -------------------- |
| 企业管理者    | 用智能体团队承接内容生产、客服、数据分析等业务 | 成本可控、过程可审、质量可追溯      |
| 技术团队负责人  | 多 Agent 协作完成软件开发全生命周期   | 任务拆解、并行协作、自动化测试部署    |
| 独立创业者    | 用最小人力运营一个产品或业务          | 一人管理一支智能体团队，快速出活     |
| AI 应用开发者 | 构建垂直行业的多智能体解决方案         | 灵活的 Agent 接入、可编程的工作流 |

### 1.4 核心差异

| 市面方案         | 局限性            | 本系统解决方式                    |
| ------------ | -------------- | -------------------------- |
| 单体 Agent     | 无协作、无流程、无记忆沉淀  | 多智能体组织化协作 + 知识库沉淀 + 自我进化   |
| Agent 框架     | 面向开发者、无治理、模型绑定 | 可视化创作 + MaaS 多模型调度 + 三原则治理 |
| 工作流平台        | 节点是工具调用，无角色概念  | 智能体有身份职能、有学习能力、有决策权限       |
| 项目管理 + AI 插件 | AI 是附属功能       | 智能体就是员工，系统就是公司             |

## 二、设计总纲：三原则

**可观测 · 可治理 · 可控风险** 是本系统所有设计决策的底层约束，贯穿从基础设施到前端交互的每一层。三原则不是单独的功能模块，而是渗透在每个能力域中的设计约束。

|原则|定义|核心问题|
|---|---|---|
|**可观测**|系统运行的每一个环节都可以被看见、被度量、被追溯|"现在发生了什么？为什么会这样？"|
|**可治理**|人类决策者在任何时刻都能介入、调整、纠偏智能体行为|"谁有权做什么？流程是否合规？"|
|**可控风险**|智能体的自主行为始终在预设的安全边界内运行|"最坏情况是什么？损失上限是多少？"|

后续各章节在每个能力模块中以 `[可观测]` `[可治理]` `[可控风险]` 标注该模块如何落地三原则。

![[01.png]]

### 3.1 MaaS 模型调度层（Model as a Service）

> 📎 图形参见：[[02-MaaS模型调度层.excalidraw]]

![[02.png]]
#### 3.1.1 设计目标

不同智能体执行不同任务时，对模型能力的需求差异很大：CEO Agent 做战略决策需要最强推理模型，客服 Agent 做日常回复用轻量模型即可。MaaS 层的作用是将"模型选择"从 Agent 定义中解耦，由平台统一调度，实现成本最优、能力最优的智能分配。

#### 3.1.2 模型注册中心

统一纳管所有可用模型资源，每个注册模型携带标准化的能力标签：推理强度等级、上下文窗口大小、支持的模态（文本/图像/代码）、每 Token 单价、平均延迟。

|模型来源|接入方式|典型场景|
|---|---|---|
|云端商业模型|API Key + Endpoint 注册|OpenAI / Anthropic / DeepSeek / 百度文心 / 阿里通义|
|企业私有部署|内网 Endpoint 注册|vLLM / TGI 部署的企业专属模型|
|本地推理|本机进程自动发现|Ollama / llama.cpp / LM Studio|
|特化模型|模型仓库拉取|代码生成专用模型、图像理解模型、嵌入模型|

#### 3.1.3 智能路由引擎

根据任务需求自动选择最优模型，支持三种路由策略：

```yaml
routing_policy:
  # 策略一：按角色匹配
  role_based:
    ceo: { prefer: "claude-opus-4", fallback: "gpt-4o" }
    developer: { prefer: "claude-sonnet-4", fallback: "deepseek-coder" }
    customer_service: { prefer: "deepseek-chat", fallback: "qwen-turbo" }

  # 策略二：按任务类型匹配
  task_based:
    strategic_planning: { min_reasoning_level: "high", prefer_cost: false }
    code_generation: { require_capability: "code", prefer_cost: true }
    content_writing: { min_reasoning_level: "medium", prefer_cost: true }
    data_extraction: { min_reasoning_level: "low", prefer_cost: true }

  # 策略三：按预算约束降级
  budget_aware:
    when_budget_remaining < 20%: { force_downgrade: true, max_tier: "medium" }
    when_budget_remaining < 5%: { force_downgrade: true, max_tier: "low" }
```

#### 3.1.4 配额管控引擎

多维度的模型资源管控：

- **公司级配额**：全公司每月模型调用总预算
- **部门级配额**：按部门分配月度预算上限
- **Agent 级配额**：单个 Agent 的月度 / 单次调用上限
- **模型级配额**：限制高成本模型的使用频次（如 Opus 级模型每日限 N 次）
- **突发弹性**：预算告警 → 自动降级 → 超支冻结的三级熔断

**三原则落地：**

- `[可观测]` 模型调用链路全程追踪——哪个 Agent、执行什么任务、路由到哪个模型、消耗多少 Token、响应时间多少，全部可查
- `[可治理]` 路由策略可随时调整；管理员可手动指定某 Agent 必须/禁止使用某模型
- `[可控风险]` 三级熔断机制确保不会出现预算失控；模型降级不中断业务，只降低推理质量

### 3.2 AI Agent 引擎（自研·可进化）

> 📎 图形参见：[[03-AI-Agent引擎.excalidraw]]

![[03.png]]
#### 3.2.1 设计目标

市面 Agent 框架的智能体是"无状态"的——每次执行都是一张白纸，能力上限完全取决于底层模型。本系统自研的 Agent 引擎让每个智能体具备**自然进化与持续学习能力**：Agent 在工作中积累经验、从反馈中修正行为、在协作中学习同伴的长处，越用越强。

#### 3.2.2 认知内核（Cognitive Core）

每个 Agent 运行时，认知内核负责组装完整的执行上下文：

```
执行上下文 = 角色人设
           + 当前任务指令
           + 目标传导链（为什么做）
           + 相关经验记忆（以前类似任务怎么做的）
           + 挂载技能（能用什么工具）
           + 组织上下文（我在团队中的位置、协作者是谁）
           + 约束规则（预算限制、权限边界、安全红线）
```

认知内核不是简单的 Prompt 拼接，而是有优先级、有冲突解决机制的上下文编排。当安全红线与任务指令冲突时，安全红线始终优先。

#### 3.2.3 经验记忆系统

Agent 的记忆分为三层，模拟人类的记忆结构：

|记忆层|生命周期|内容|写入方式|
|---|---|---|---|
|**工作记忆**|单次任务执行期间|当前任务的中间状态、对话上下文|自动维护|
|**情景记忆**|跨任务持久化|历史任务的关键决策、成功/失败案例、反馈记录|任务结束时自动提取|
|**能力记忆**|长期沉淀|抽象化的工作方法、最佳实践、领域知识|学习引擎定期蒸馏|

一个产品经理 Agent 在处理 100 个需求后，其情景记忆中积累了大量"什么样的需求描述容易导致开发偏差""哪类功能需求用户反馈最积极"等实战经验，这些经验会被学习引擎蒸馏为能力记忆，内化为 Agent 的判断力。

#### 3.2.4 学习引擎（自然进化机制）

通过四种学习路径实现持续成长：

**路径一：任务反馈学习**——任务执行后获得反馈（人类评价 / 下游 Agent 反馈 / 自动化指标），正向反馈强化成功模式写入能力记忆，负向反馈分析失败原因生成修正规则。

**路径二：自我反思学习**——Agent 每完成一个任务周期，自动触发反思：回顾关键决策点 → 评估实际效果 → 提取可复用经验 → 调整未来策略。

```yaml
self_reflection:
  trigger: "task_completed"
  process:
    - review_decision_points: "回顾本次任务中的关键决策点"
    - evaluate_outcomes: "评估每个决策的实际效果"
    - extract_lessons: "提取可复用的经验教训"
    - update_behavior: "调整未来同类任务的处理策略"
  output: reflection_note
```

**路径三：协作观察学习**——同一工作流中上下游 Agent 的输出质量作为间接反馈；高绩效 Agent 的工作模式可被提取为"最佳实践"；管理者 Agent 可将验证过的最佳实践推送给所有下属。

**路径四：知识库驱动学习**——任务涉及未知领域时 Agent 主动检索 LLM Wiki 获取领域知识；人类专家更新知识库后，相关 Agent 在下次心跳时自动感知并学习。

#### 3.2.5 进化评估器

量化追踪每个 Agent 的能力成长：

|评估维度|指标|度量方式|
|---|---|---|
|**任务质量**|一次通过率、返工率、人类评分均值|按任务类型分类统计|
|**决策效率**|平均任务耗时、Token 消耗趋势|相同类型任务的时序对比|
|**学习效果**|同类任务表现趋势线、新能力获取数|时间序列分析|
|**协作能力**|下游 Agent 满意度、返工触发率|上下游反馈统计|
|**风险表现**|触发安全红线次数、异常率|安全审计日志统计|

进化评估器定期生成"Agent 成长报告"，展示能力雷达图的变化趋势。如果检测到 Agent 能力退化（某段时间任务质量持续下降），自动触发预警并建议干预措施。

**三原则落地：**

- `[可观测]` Agent 的每一次学习、每一条记忆、每一步进化都有记录，管理者可以查看 Agent 为什么做出某个决策
- `[可治理]` 人类可以审核 Agent 的学习成果，删除不当记忆，手动注入正确知识；可以冻结、重置或回退 Agent 的进化状态
- `[可控风险]` 学习引擎写入的规则需经过安全检查，不允许 Agent 学习到绕过安全约束的"经验"；能力退化自动预警

### 3.3 LLM Wiki 知识库引擎（自研·人机共享）

> 📎 图形参见：[[04-LLM-Wiki知识库引擎.excalidraw]]

![[04.png]]
#### 3.3.1 设计目标

传统知识库（如 Confluence、Notion）是"人写人读"的；传统 RAG 知识库是"人写 AI 读"的。本系统自研的 LLM Wiki 是**人机共建、人机共读**的——人类和智能体共同贡献知识、共同检索使用、共同维护更新，实现组织知识在人与 AI 之间的无缝流转。

#### 3.3.2 知识采集层

知识从两个方向持续流入：

**人类方向：**

|输入方式|说明|
|---|---|
|Wiki 编辑器|人类直接编写和维护知识文档|
|文档导入|批量导入企业已有文档（Word / PDF / Markdown / HTML）|
|对话沉淀|人类与 Agent 交互中产生的高价值问答可一键存入|
|外部爬取|按需从指定数据源抓取并结构化|

**智能体方向：**

|输入方式|说明|
|---|---|
|任务总结|Agent 完成任务后自动提取的经验总结|
|研究产出|数据分析 Agent、调研 Agent 的研究报告|
|最佳实践|学习引擎从高绩效 Agent 中蒸馏出的工作方法|
|知识发现|Agent 在工作中发现的新知识点或知识矛盾|

所有智能体写入的知识默认标记为"AI 生成·待审核"状态，需经过知识治理流程后才正式纳入知识库。

#### 3.3.3 知识加工层

原始知识进入知识库后，经五步加工处理：

```
原始文档/内容
    ↓
① 智能切片 ── 按语义自动分段，保持知识点完整性
    ↓
② 结构化抽取 ── 提取实体、关系、属性，构建知识图谱节点
    ↓
③ 多模态嵌入 ── 文本/图表/代码分别生成向量嵌入
    ↓
④ 关联编织 ── 自动发现与已有知识的关联关系
    ↓
⑤ 质量评分 ── 评估知识的完整性、一致性、时效性
    ↓
入库（向量库 + 图谱库 + 全文索引）
```

#### 3.3.4 知识服务层

为人类和智能体提供统一但差异化的知识访问：

|使用者|访问方式|呈现形式|
|---|---|---|
|**人类用户**|Wiki 浏览器 / 搜索 / 问答|结构化文档 + 知识图谱可视化 + 自然语言问答|
|**智能体**|API 调用 / 自动注入|结构化知识片段 + 相关上下文 + 引用溯源|
|**工作流节点**|流程上下文自动关联|与当前任务相关的知识自动附加到 Agent 上下文|

知识检索采用**混合检索**策略：向量语义检索 + 关键词全文检索 + 知识图谱遍历，三路结果融合排序，确保召回质量。

#### 3.3.5 知识治理层

|治理机制|说明|
|---|---|
|**版本管理**|每次知识变更生成新版本，支持差异对比和任意回滚|
|**贡献溯源**|每条知识标记来源（人类 / 哪个 Agent / 哪次任务），可追溯产生过程|
|**质量评估**|定期检测时效性（过期标记待更新）、一致性（矛盾标记待裁决）、引用频率（低价值标记归档）|
|**权限控制**|按知识域、密级、部门设置读写权限；涉密知识加密存储|
|**审核流程**|AI 生成的知识需经人类审核或交叉验证后才进入正式库；支持高权限 Agent 审核低权限 Agent 的产出|
|**知识冲突裁决**|新写入知识与已有知识矛盾时，自动标记冲突并提交裁决（人类或指定权威 Agent）|

**三原则落地：**

- `[可观测]` 每条知识的来源、变更历史、引用次数、质量评分全部透明可查
- `[可治理]` 人类对知识库有最终裁决权；AI 产出的知识必须经过审核流程；可随时回滚任何变更
- `[可控风险]` 知识权限分级防止敏感信息泄露；错误知识的传播有版本控制和冲突检测兜底

## 四、产品基础能力

### 4.1 多智能体协作、通讯与数据共享

#### 4.1.1 组织架构引擎

```
公司 (Company)
├── 目标使命 / 全局预算 / 治理规则
├── 部门 (Department)
│   ├── 职能分组 / 部门预算 / 数据权限
│   └── 智能体 (Agent)
│       ├── 角色 / 职称 / 汇报关系
│       ├── 技能集合 / 工作方式 / 经验等级
│       └── 个人预算 / 模型配额 / 运行状态
└── 项目组 (Team)
    ├── 跨部门临时协作单元
    └── 项目目标 / 成员 / 交付物
```

关键设计原则：

- **严格汇报链**：每个智能体向且仅向一个上级汇报，支持任务升级与逐级委派
- **多公司隔离**：单一系统实例可运行多个独立公司，组织数据、任务数据、知识库完全隔离
- **动态组队**：支持跨部门按项目组建临时协作团队，项目结束自动解散
- **可视化展示**：前端实时渲染组织架构图，支持拖拽调整层级与汇报关系

**三原则落地：**

- `[可观测]` 组织架构实时可视化；任何 Agent 的状态、负载、健康度一目了然
- `[可治理]` 决策者可随时调整组织架构、冻结/终止任何 Agent、重新分配汇报关系
- `[可控风险]` Agent 的权限严格受限于其在组织中的位置，越权操作被自动拦截

#### 4.1.2 通讯机制

|通讯模式|方向|触发方式|典型场景|
|---|---|---|---|
|**任务委派**|上级 → 下级|管理者 Agent 拆解目标后分配子任务|CTO 将技术方案拆为前后端开发任务|
|**状态上报**|下级 → 上级|任务状态变更时自动触发|开发完成后通知项目经理进入测试|
|**@提及**|任意 → 指定|任务评论中 @某个 Agent|测试发现 Bug 后 @对应开发者|
|**广播通知**|系统 → 全体/组|目标变更、预算告警等事件|公司目标调整，全员收到新方向|
|**数据管道**|Agent A → Agent B|工作流节点间的数据流转|设计稿完成后自动流转至开发节点|

核心协议流程：

```
定时/事件唤醒 → 身份确认 → 获取待办任务 →
原子锁定任务（防止重复执行）→ MaaS 分配模型 →
加载相关记忆与知识 → 执行工作 →
更新状态 / 写入经验 → 释放任务 → 会话状态持久化
```

**三原则落地：**

- `[可观测]` 所有通讯记录写入不可篡改的审计链，支持完整的决策回溯
- `[可治理]` 通讯权限遵循组织架构，Agent 不能越级通讯或私自广播
- `[可控风险]` 原子任务锁定杜绝重复执行；通讯频率限制防止消息风暴

#### 4.1.3 数据共享体系

|层级|数据范围|访问控制|
|---|---|---|
|**全局知识库（LLM Wiki）**|公司级知识、制度、产品文档|全体只读，授权角色可写|
|**部门数据**|部门文档与历史产出|部门内读写|
|**项目数据**|项目上下文、交付物、讨论|项目成员读写|
|**任务数据**|单任务的输入输出与对话|执行者读写 + 上级可查|
|**Agent 私有记忆**|经验记忆、学习笔记|仅该 Agent，管理员可审计|

**目标传导链**：每个任务携带完整链路——公司使命 → 战略目标 → 项目目标 → 具体任务，确保每个 Agent 理解"为什么做"。

#### 4.2.3 工作方式

智能体支持五种工作触发模式，可为同一 Agent 同时配置多种：

|工作模式|机制|适用场景|
|---|---|---|
|**定时心跳**|可配置周期自动唤醒，检查待办并执行|日报生成、数据同步、定期巡检|
|**事件驱动**|被任务分配、@提及、审批结果等事件触发|任务处理、协作响应、异常处理|

|**管道触发**|上游 Agent 完成工作后自动触发下游|工作流中的链式协作|
|**持续运行**|长驻后台监听特定信号源|客服 Agent、监控告警 Agent|

#### 4.2.4 技能系统

智能体的能力通过可插拔的技能系统扩展，技能在运行时按需加载，无需重建 Agent：

|类别|内置技能|自定义技能|
|---|---|---|
|数据|API 调用、数据库操作、搜索引擎|行业知识库检索、业务规则引擎|
|文件|文件读写、图表生成、Wiki 读写|企业 SOP 规程、专属算法模型|
|集成|代码执行、MCP 工具连接|外部系统对接、自定义工具集|

技能管理机制：

- **运行时注入**：Agent 执行任务时按需加载所需技能，运行结束后释放
- **技能组合**：一个 Agent 可同时挂载多个技能，形成复合作业能力
- **版本管理**：技能定义支持版本控制，可按需回滚至历史版本
- **权限约束**：特定技能可按角色和部门限制使用范围（如数据库写操作仅限 DBA 角色）

### 4.3 智能体工作流程编程

> 📎 图形参见：[[05-工作流编排引擎.excalidraw]]

![[05.png]]
#### 4.3.1 工作流编排引擎

```
可视化画布编辑器 ←→ 流程 DSL (YAML) ←→ 执行运行时
```

三者互相同步：用户在画布上拖拽设计流程，系统自动生成 DSL；也可直接编写 DSL，画布自动渲染；运行时按 DSL 定义调度各 Agent 执行。

#### 4.3.2 流程原语（8 种）

|原语|符号|说明|
|---|---|---|
|**顺序执行**|`→`|A 完成后触发 B|
|**并行执行**|`∥`|A 和 B 同时执行，互不阻塞|
|**条件分支**|`◇`|根据上游输出选择执行路径|
|**循环迭代**|`↻`|重复执行直到满足退出条件|
|**汇聚等待**|`⊕`|等待所有并行分支完成后继续|
|**人工审批**|`✋`|暂停流程，等待人类决策者审核|
|**事件等待**|`⏳`|暂停流程，等待外部事件信号|
|**异常处理**|`⚠`|定义执行失败时的重试或回退逻辑|

#### 4.3.3 工作流 DSL 示例

```yaml
workflow:
  name: "需求到上线全流程"

  steps:
    - id: collect_requirements
      agent_role: "product_manager"
      action: "收集整理用户需求，输出需求文档"
      knowledge_inject: ["product_wiki/requirements_template"]

    - id: review_requirements
      type: approval_gate
      approver: "board"
      condition: "requirement_doc.impact_level >= 'high'"

    - id: design_and_plan
      type: parallel
      branches:
        - id: ui_design
          agent_role: "ui_designer"
          model_override: "claude-sonnet-4"

        - id: tech_plan
          agent_role: "architect"

    - id: design_complete
      type: join
      wait_for: [ui_design, tech_plan]

    - id: implementation
      agent_role: "developer"
      budget_limit_cny: 200.00
      risk_checkpoint: true

    - id: testing
      agent_role: "tester"
      retry: { max_attempts: 3, on_failure: "return_to:implementation" }

    - id: deploy
      agent_role: "devops"
      condition: "test_report.pass_rate >= 0.95"
      post_action: "wiki_publish:deployment_record"
```

#### 4.3.4 治理与审批门控

|治理节点|触发条件|处理方式|
|---|---|---|
|**招聘审批**|Agent 请求创建下属|暂停，等待决策者批准|
|**预算门控**|预计成本超阈值|暂停，等待预算审批|
|**策略审批**|管理层方案产出|暂停，等待决策者审核|
|**模型升级审批**|Agent 请求使用更高等级模型|暂停，等待 MaaS 管理员审批|
|**异常升级**|连续失败或异常行为|自动冻结 Agent 并通知决策者|
|**质量门控**|交付物不达标|退回上游或升级处理|
|**知识审核**|Agent 写入知识库|知识进入待审核状态|

### 4.4 智能体应用载体（Adapter 层）

#### 4.4.1 Adapter 架构 [[07-Adapter架构.excalidraw]]

系统本身是控制平面，不直接运行 Agent。智能体在各自执行环境中运行，通过标准化的 Adapter 接口与控制平面、MaaS 层、知识库引擎通讯。

![[07.png]]

这种分离架构的核心优势：Agent 的执行技术可以任意替换和升级，控制平面保持稳定；同一套组织架构和业务流可以驱动完全不同技术栈的智能体团队。

#### 4.4.2 Adapter 类型

|Adapter 类型|执行方式|适用场景|
|---|---|---|
|**LLM API Adapter**|经由 MaaS 层调用大模型 API|文本处理、分析决策、内容生成|
|**CLI Agent Adapter**|启动本地 CLI 工具进程|编程开发、代码审查、系统运维|
|**MCP Adapter**|MCP 协议连接外部工具服务|数据库操作、文件管理、三方集成|
|**HTTP Webhook Adapter**|调用外部 HTTP 端点|对接企业内部 API、SaaS 平台|
|**Process Adapter**|启动本地脚本或程序|Python 数据管道、批处理|
|**Composite Adapter**|组合多个 Adapter 为复合能力|同时需要模型推理和代码执行|

#### 4.4.3 Adapter 接口规范

每个 Adapter 实现三个标准模块：

```
Server 模块（必须）
  ├── execute(context) → RunResult    # 执行 Agent 心跳
  ├── diagnose() → EnvironmentDiag    # 环境健康检查
  └── parseUsage(output) → CostData   # 解析执行成本

UI 模块（推荐）
  ├── ConfigForm                       # Agent 创建时的配置表单
  ├── RunViewer                        # 执行过程实时展示组件
  └── OutputParser                     # 输出内容格式化

CLI 模块（可选）
  ├── formatOutput(run) → string       # 命令行格式化输出
  └── watchMode(agentId)               # 终端实时监控
```

开发者只需实现 Server 模块即可接入新的 Agent 运行时，UI 和 CLI 模块可渐进补充。

## 八、典型应用场景

### 场景一：智能体软件开发团队

组建 CEO → CTO → 前端/后端/测试/运维的开发团队。MaaS 为架构师分配强推理模型，为日常编码分配高性价比模型。Agent 引擎让开发者 Agent 从历次 Code Review 中学习代码风格偏好。LLM Wiki 沉淀技术方案和部署手册，新 Agent 加入即可获取全部项目知识。

### 场景二：内容生产工厂

组建内容总监 → 选题编辑 → 写手 → 校审 → 发布运营的流水线。写手 Agent 从审稿反馈中持续学习写作风格，进化评估器追踪稿件一次通过率的提升曲线。LLM Wiki 维护品牌调性指南和选题库，确保所有 Agent 的产出风格一致。

### 场景三：智能客服团队

客服 Agent 持续运行处理用户消息，MaaS 在高峰期自动切换至高并发低延迟模型，低峰期切回高质量模型。Agent 引擎将高分对话沉淀为经验记忆，质检 Agent 定期将典型案例写入 LLM Wiki 作为培训材料。

### 场景四：数据分析部门

数据管道按周/月驱动采集 → 清洗 → 分析 → 报告。分析 Agent 通过学习引擎积累行业分析框架，在进化评估器中可追踪其分析准确率的提升。研究报告自动写入 LLM Wiki，决策者和其他 Agent 均可检索引用。

## 九、游戏内容开发业务智能体 

游戏研发是这套系统最天然的落地场景之一——游戏项目本身就是多工种、长周期、强协作的团队工程。下面从五个维度来讲。

游戏研发团队的组织架构和核心工作流：

![[game.png]]


"公司"结构——策划、美术、程序、QA、运营五大工种，10-50 个智能体互相协作，中间有大量跨部门交接、版本迭代和反馈循环。这恰好对齐了系统的四级组织架构（制作人→部门主管→工种Agent→项目组）。

传统游戏研发的痛点全部被系统能力覆盖：

**策划文档写了没人看** → LLM Wiki 让 GDD 变成人机共用的活文档，Agent 直接从中取用需求，人类直接在上面搜问答。

**高级人才贵且难招** → MaaS 为不同工种匹配不同等级模型，策划用强推理做玩法设计，QA 用轻量模型跑批量回归测试，一个项目同时调用 3-4 种模型，成本最优。
